# Commit and push BenchMaster changes

Use this skill when the user asks to commit, push, or commit and push work in this repository. Treat the current user request as authorization for those Git actions, but do not include unrelated changes in the commit.

## Workflow

1. Read the repository instructions and inspect `git status`, the current branch, upstream, and the full diff. Identify generated files, unrelated edits, secrets, and untracked files. Never stage unrelated files just to make the tree clean.
2. Classify the intended change from the diff before choosing checks or writing a commit message. Use `fix` for correcting a defect or regression, `feat` for user-visible capability, `perf` for performance improvements, `refactor` for behavior-preserving code restructuring, `style` for visual/UI changes that do not add capability, `docs` for documentation, `test` for tests, `build` for build/dependency tooling, and `chore` for maintenance that does not fit better elsewhere. For mixed changes, choose the primary user-facing outcome; split into separate commits only when the changes are independent and clearly separable. Do not classify based on branch name alone.
3. Infer the checks from the changed files. For frontend or shared application changes, run `npm run build --workspace frontend` (or the root `npm run build` when backend changes also need coverage). The Angular production build enforces `anyComponentStyle` budgets in `frontend/angular.json`. Review warnings, especially styles near the error threshold, and report them accurately.
4. For backend changes, run the relevant backend build. Run tests or other checks when they exist and are relevant; do not invent tests or alter budget configuration merely to hide a failure.
5. When a build or relevant check fails, read the complete error output, identify the first actionable cause, and attempt a focused source or configuration fix when it is feasible, safe, and within the requested change. Follow the failure through its underlying cause instead of suppressing the error. For example, reduce an oversized component stylesheet when it exceeds an Angular style budget; never raise the budget just to make the build pass. Do not modify unrelated behavior, weaken checks, or make speculative changes. After each fix, rerun the failing check and any directly affected checks. If the fix succeeds, include the correction in the requested commit and push it together with the intended changes; use a commit type and subject that describe the resulting change. If the cause is external, ambiguous, out of scope, or cannot be fixed confidently, stop before committing or pushing and report the error, attempted fix, and concrete blocker. Never claim a check passed unless it was rerun successfully.
6. Review the final diff and `git diff --check`. Stage only the files needed for the requested change and any focused build correction made under step 5. Write a recognizable Conventional Commit subject in the form `<type>(<optional-scope>): <imperative summary>`, using the classification above, lowercase type/scope, and a short summary that says what changed. Examples: `fix(auth): preserve session cookie on refresh`, `feat(training): add coach session planner`, `docs: explain local setup`. Omit the scope if it does not make the subject clearer. Add `!` after the type/scope for a breaking change and explain it in the commit body. Avoid vague subjects such as `updates`, `misc fixes`, or `changes`, and do not force a scope when none fits. If repository-specific commit instructions require another format, follow them while keeping the change type easy to scan.
7. Push the requested branch to its configured upstream. If no upstream exists, inspect remotes and branch state and report the exact command or destination needed rather than guessing. If checks still fail after feasible fixes, credentials are unavailable, or the push is rejected, stop and report the concrete blocker without claiming success.
8. Afterward, verify the commit hash and push result, and summarize the change classification, commit subject, checks (including any failure and successful retry), warnings, committed files, and any unrelated work left untouched.

## BenchMaster build details

- Root `npm run build` builds the backend and frontend workspaces.
- `npm run build --workspace frontend` runs the Angular production build.
- Production Angular budgets are in `frontend/angular.json`. Component styles warn above 10 kB and fail above 12 kB. When a style exceeds the error budget, first try to reduce or consolidate the component stylesheet while preserving behavior. Include the focused fix in the requested commit and push it after the build passes. Do not raise the project budget unless the user specifically asks for a budget policy change.
